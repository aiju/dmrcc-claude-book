Chapter 5

Parsing Expressions

Everything in c0 that is not an expression is parsed by recursive descent: a routine for each kind of statement or declaration, reading tokens and calling other routines. Expressions are different. They are parsed by a single routine, tree (1817–2019), using what its comment calls “the classical bottom-up, priority-driven scheme”. It is about two hundred lines long, has no recursion, and consists almost entirely of gotos.

The method

An operator-precedence parser keeps two stacks: one of operands, which are trees built so far, and one of operators not yet applied. It reads the expression from left to right. Operands are pushed onto their stack as they arrive. When an operator arrives it is compared with the operator on top of the stack. If the new one binds more tightly, it must be applied first, so it is pushed. If not, the one on the stack is applied now: it is popped, together with its operands, and the resulting tree is pushed back onto the operand stack. This is called a reduction, and reductions continue until the new operator does bind more tightly than whatever is left on top, at which point it is pushed.

tree keeps three stacks, declared at 1821: opst for operators, prst for their priorities, and the global cmst for operands. The priority of an operator is normally a property of the operator, but keeping a separate stack of them lets tree push some operators with a priority different from the one they had on arrival, and that turns out to be the key to handling parentheses, calls and postfix operators.

The bottom of the operator stack holds a marker, SEOF, with priority 6 (1830–1831). Any token with a priority of 6 or less that arrives with nothing but SEOF above it ends the expression. That includes ;, ), ], {, and every other token that is not an operator, since they all have priority 0. So the parser needs no knowledge of what may follow an expression: if (a), x[a], return(a); and a; all end the same way, with the terminating token pushed back for the caller (1978–1981).

The priorities

Priorities come from the table opdope in c05.c (4165–4277). Each entry is a word of flags describing the operator: whether it takes two operands, whether its operand must be an lvalue, whether it is a relational or an assignment operator, and so on (4152–4163). The high bits, starting at bit 9, hold the priority, which tree extracts with (opdope[o]>>9) & 077 (1950). Written in octal, as the table is, the priority is simply the first two digits: + is 030101, priority 030 or 24.

Grouping is decided by the flag RASSOC, 0200. When the incoming operator has the same priority as the one on the stack, it is pushed if it groups to the right and the stacked one is reduced if it groups to the left (1955). So a-b-c reduces a-b before reading c, while a=b=c stacks both assignments.

This table is almost exactly the precedence of C today, including the notorious placing of & below ==, which is a relic of the days when & also served as &&. There is one difference. Modern C gives &, ^ and | three distinct levels. Here ^ and | share one, so they simply group left to right. The real compiler confirms it:

prec.c

main()
{
        int a, b;

        a = 1;
        b = 3;
        printf("%d %d\n", 1 | 2 ^ 3, 6 & 3 == 3);
        printf("%d\n", a++ + ++b);
        printf("%d %d\n", a, b);
}

a.out

0 0
5
2 4

In modern C the first number would be 1: 1 | (2 ^ 3). Here it is (1 | 2) ^ 3, which is 0. The compiler computed it at compile time; the generated code is just clr -(sp).

Reading the code

The body of tree is a loop that starts at the label advanc, reads a token and switches on it (1834–1943). The flag andflg records what kind of token is expected next. It is 0 when an operand is expected, at the start and after an operator, and 1 when an operator is expected, after an operand. Its name suggests an “and” of operands: once it is set, another operand would be a syntax error (1870–1878).

That one flag resolves all of the ambiguities the lexer left behind:

  • * and & are binary when an operand has just been seen and unary otherwise (1909–1917).
  • - is binary or unary in the same way (1893–1907). A unary minus directly in front of a floating constant is folded into the constant.
  • ++ and -- after an operand are postfix, which is made by adding 2 to the token number to turn INCBEF into INCAFT (1880–1884).
  • ( after an operand starts a function call (1919–1930). A ( immediately followed by ) is a call with no arguments, MCALL, which counts as an operand, so andflg stays 1.

Operands are names, constants and strings. A name is turned into a tree node by copname. A name that has never been declared gets special treatment (1837–1853). If it is followed by ( it is taken to be a function returning int, which is why functions need not be declared. In an initializer, it is taken to be an external. Otherwise it is assumed to be a label that has not been defined yet, which is how goto can refer forward: a label is represented as an array, and its label number is allocated now. If it never is defined, blkend reports it as undefined at the end of the function, the message seen in chapter 2. A string constant becomes the name of a static array of char labelled by the string's number, and its text is written out immediately (1865–1868).

The comparison p>ps decides between pushing and reducing. When the new operator is pushed, three kinds get a new priority as they go on the stack. Postfix ++ and -- are stacked with priority 37, higher than anything that can arrive, so they are reduced as soon as the next token appears. (, [ and the call operator arrive with priority 30, high enough to be pushed on top of anything, but are stacked with priority 4, lower than any operator that can follow them. So everything between the brackets is reduced down to the bracket, and nothing more, until the closing ) or ], whose priority 2 is lower still, pops the bracket itself.

The reduce side is at 1975–2013. Most operators are handed to build, which pops their operands, makes the node and pushes it; then control returns to opon1 to compare the new operator with the next one down. The brackets are special. A ( that meets its ) simply disappears, and a [ meeting ] builds a subscript. A call is built when its ) arrives, from the function and the tree of its arguments, which the comma operator has already joined into a left-leaning chain of , nodes. The increment operators are given a second operand, the constant 1; build will scale it if the operand is a pointer.

Commas and colons in initializers

One complication remains. In an initializer list, {1, 2, 3}, and after case, the comma and the colon are not operators but separators. When the global initflg is set, tree gives them priority 5 instead of their usual 7 and 12 (1951–1952). Five is below the end marker's 6, so a comma or colon then ends the expression. conexp, which reads the constant expressions of array bounds, case labels and bit-field widths, sets the flag (2610–2620).

What is not here



Some things a modern reader expects are absent because the language did not have them yet.
There are no casts, since there are no type names that could appear in an expression, and
sizeof can only be applied to an expression, never to a type. There is no
unsigned, so no conversions involving it. And there is no typedef, which spared
the Sixth Edition compiler the problem that later bedevilled C parsers: deciding whether a name is
a type or a variable.



What tree leaves on the operand stack is not quite the tree that was written. As each
node is made, build inserts conversions, scales pointer arithmetic, rewrites subscripts and
structure references, checks types and folds constants. That is the subject of the next chapter.
