Chapter 9

Rewriting Trees

The second pass begins where the first ended: with a file of records, most of them pieces of expression trees in postfix order. Before generating any code, c1 rebuilds each tree and passes it through a set of routines that rewrite it into a shape better suited to the machine. This chapter covers that preparation. The next two cover code generation proper.

From here on, much of what is said is illustrated by traces. For this book a copy of c1 was rebuilt on the simulated PDP-11 with one extra source file that prints each tree as it is read, prints it again after optimization, and records every code-table entry used to compile it. With the trace records removed, its output is identical to the real c1's for every example. The scripts are in the repository under tools/c1trace.

Reading the file

c1's main (4878–4916) opens the two temporary files and the output file, and calls getree twice: once for the main file and once for the strings, with a .data between them. getree (6429–6617) is a loop over records. Records that are simple commands print their assembly language immediately: a label, a jump, a segment change, the entry sequence for a function (6494–6501). Tree records build nodes on an explicit stack, expstack, and EXPR hands the finished tree to the code generator (6535–6544):

c11.c
 6535          case EXPR:
 6536                  line = getw(ascbuf);
 6537                  if (sp != &expstack[1]) {
 6538                          error("Expression input botch\n");
 6539                          exit(1);
 6540                  }
 6541                  nstack = 0;
 6542                  rcexpr(optim(*--sp), efftab, 0);
 6543                  spacep = treespace;
 6544                  break;

optim is applied to the tree first, and then rcexpr compiles it with the table efftab, which means “for its side effects”, since the value of an expression statement is not wanted. The space for tree nodes is reclaimed after every expression, as in c0.

The node layouts of c1 (4557–4598) look like c0's, but the third word of every node is now degree, an estimate of the number of registers needed to evaluate it, which the optimizer fills in. Name nodes are rearranged too: class and register number are packed into one word as two bytes, followed by an offset and a location, and an external name is stored directly after the node, eight bytes of it, so the node for _printf is nine words long.

Names become addresses

The PDP-11 has several addressing modes that combine a register with an offset: n(r), _x(r), (r)+ and so on. c1 recognises such operands at the tree level and represents each by a single name node, so that by the time code is generated, an operand that can be written as one address is one leaf. To do this it adds three storage classes to those of c0 (4804–4806):

ClassMeaningWritten
OFFSoffset from a register-10(r5), 4(r2), (r4)
XOFFSexternal name indexed by a register_m(r1)
SOFFSstatic label indexed by a registerL5(r1)

and two operators, AUTOI for *r++, written (r)+, and AUTOD for *--r, written -(r). The very first thing optim does is turn every automatic variable into an OFFS name on r5 (6670–6674). The rest is done by unoptim, the optimizer for unary operators (6816–6934), whose case for * does most of the work (6858–6890):

  • *&x is x.
  • *r, with r a register variable, is OFFS with offset 0: (r4).
  • *r++ and *--r become AUTOI and AUTOD, if the increment matches the size of the object, which is what the type check at 6868–6869 ensures.
  • *(r + c) becomes OFFS with offset c.
  • *(r + &x) becomes XOFFS or SOFFS: _x(r), which is how arrays are subscripted with an index in a register.

The reverse happens for & (6841–6856): the address of an automatic variable is not an operand the machine can express, so &x of an OFFS name is turned into the addition of r5 and a constant.

Bit-fields are expanded here as well (6833–6839). An FSEL node is replaced by (x >> bitoffs) & mask, and the ordinary rules then turn the shift into an ash and the AND into a bic. Since the translation only produces a value, there is no way to store into a field: the second pass could not have compiled a field assignment even if the first had allowed it.

Rewrites for the PDP-11

Several rewrites in optim (6658–6814) are marked in the comments as “PDP-11 special”. Each works around a gap in the instruction set.

  • AND. The PDP-11 has bic, which clears the bits of one operand that are set in the other, but no AND. So a & b becomes a NAND ~b, where NAND is the compiler's name for bic's operation (6687–6696); similarly =& becomes =&~ (6729–6738). When b is a constant, the complement is folded into it, so x & 7 costs a single bic $-10. When the value is only being tested, as in if (a & 010), the code generator turns the operator into TAND to use the bit instruction instead (5076–5086); see gen.c in the next chapter.
  • Right shifts. ash shifts left by a positive count and right by a negative one, so x >> n becomes x << -n, except for a shift by one, for which there is asr (6782–6799).
  • Subtraction of a constant becomes addition of its negation (6754–6764), so that it can join a chain of additions and be combined with other constants. For a double constant, negation means flipping the sign bit of its first word.
  • Long multiplication and division have no instructions, and become calls to library routines through hardlongs (7245–7270).

Relational operators get two treatments of their own (6701–6713). The operands are swapped, with the operator reversed to compensate using the table maprel, so that the more complicated operand comes first. And a comparison of a char with a small constant marks the constant as a char too, so that a single cmpb can be used without widening the character first.

Degrees

Every operator node leaves optim with its degree filled in. The degree approximates the number of registers the node needs, computed bottom up in the way now called Sethi-Ullman numbering: if both operands need the same number of registers, the node needs one more, since the first result must be held while the second is computed; otherwise it needs as many as the more demanding operand, which can be done first (6808–6811):

tree->degree = d1==d2? d1+islong(tree->type): max(d1, d2);

islong is 2 for a long, which lives in a pair of registers, and 1 otherwise. The degrees of leaves come from degree (5814–5833): constants count −3 and addresses −2, since they need no register at all and can appear as immediate operands; other leaves count 0, except char and float, which must be converted in a register and count 1. Multiplication and division add 2 to their operands' degrees, because they tie up a pair of registers, and a call counts 10, since it destroys the contents of every register the callee may use.

Degrees are used in two places. The code tables choose between templates by comparing an operand's degree with the number of free registers (next chapter). And the reordering routines use them to evaluate the harder operand first, so that fewer intermediate results need to be held.

Associative and commutative operators

+, *, &, | and ^ are marked COMMUTE in opdope. For them, optim calls acommute (6943–7018), which treats a whole chain of the same operator as a single list. insert (7156–7203) flattens the chain: in a + (b + (c + 3)) it collects the operands a, b, c and 3 and the three + nodes, and sorts the operands by decreasing degree. Then acommute:

  • folds all the constants, which have the lowest degree and so are at the end of the list, into one (6958–6965);
  • drops + 0, and a multiplication by 1, and replaces the whole chain by 0 if it is multiplied or ANDed by 0 (6966–6989);
  • adds a constant into the offset of an address: &x + 4 becomes the single address 4+_x (6974–6979); this is what turned &v[7] into $16+_v in chapter 6;
  • for addition, looks for common factors with distrib; and
  • rebuilds the chain as a left-leaning tree, hardest operand first, recomputing the degrees (6992–7014).

insert also applies the distributive law in one direction: a product c1 * (x + c2) inside a sum is rewritten as c1*x + c1*c2 (7176–7192), so that the constant can join the others. This is aimed squarely at subscripts: p[i+1] is *(p + (i+1)*2), which becomes *(p + i*2 + 2), and the 2 then ends up as the offset in an addressing mode.

distrib (7020–7091) goes the other way, factoring. Among the terms of a sum it looks for products by constants where one constant divides another, and rewrites c1*c2*x + c1*y as c1*(c2*x + y), repeating until no more pairs are found. The target again is address arithmetic. A two-dimensional subscript m[i][j] of an int m[10][10] arrives as m + i*20 + j*2; distrib makes it m + (i*10 + j)*2, and multiplication by 2 becomes a shift:

dist.c

int m[10][10];
int a, b, x;

f(i, j)
{
        x = m[i][j];
        x = a*4 + b*4;
        x = a*6 + b*2;
        x = (a + 3) * 5;
}

The subscript costs one multiplication, by 10 ($12 in octal), a shift, and an indexed addressing mode. a*4 + b*4 becomes (b + a)*4, and the multiplication a shift by two. a*6 + b*2 becomes (a*3 + b)*2. The last statement shows the limit of insert's rule: (a + 3) * 5 is not inside a sum, so it is left alone.

Powers of two

Multiplication and division by a power of two are turned into shifts by pow2 (6272–6289), called from rcexpr. For multiplication this is always right. For division it is not. A shift rounds towards minus infinity, while the PDP-11's div, like C, rounds towards zero, so the two disagree for negative numbers:

div.c

main()
{
        int x, y, four;

        x = -1;
        y = -7;
        four = 4;
        printf("%d %d\n", x/4, y/4);
        printf("%d %d\n", x/four, y/four);
}

a.out

-1 -2
0 -1

Dividing by the constant 4 gives −1 and −2; dividing by a variable holding 4 gives the right answers, 0 and −1. The first line was compiled to ash $-2,r0.

Since the language had no unsigned type, every int division by a constant power of two was affected. Later compilers took care to use a shift only where it gives the same answer.
