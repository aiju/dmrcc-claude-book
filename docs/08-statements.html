Functions and Statements

Statements are the easy part of c0. Every control structure in C can be expressed with three things: labels, unconditional jumps, and jumps that happen if an expression is true or false. c0 writes all three to the intermediate file as it reads each statement, using the records LABEL, BRANCH and CBRANCH, and leaves it to c1 to decide how to evaluate the conditions. This chapter goes through c02.c from a function's first line to its last.

A function

When extdef finds a function definition, it records the function's return type in the global node funcblk and calls cfunc (2711–2726):

c02.c
 2711  cfunc(cs)
 2712  char *cs;
 2713  {
 2714          register savdimp;
 2715  
 2716          savdimp = dimp;
 2717          outcode("BBS", PROG, RLABEL, cs);
 2718          declist(ARG);
 2719          regvar = 5;
 2720          retlab = isn++;
 2721          if ((peeksym = symbol()) != LBRACE)
 2722                  error("Compound statement required");
 2723          statement(1);
 2724          outcode("BNB", LABEL, retlab, RETRN);
 2725          dimp = savdimp;
 2726  }

PROG switches to the text segment, and RLABEL makes c1 print the function's name as a label, twice: once as _f: for the linker and once as ~~f: for the debugger. Then the parameter declarations are read, regvar is reset to 5 so that register variables will start at r4, and a label is allocated for the function's exit. The body is then compiled as an ordinary compound statement, with the argument 1 to say that it is the outermost one, and finally the exit label is written, followed by RETRN, which becomes jmp cret.

Every return jumps to that one exit label rather than returning directly, so every function has exactly one jmp cret. When the body's last statement is a return, the result is a jump to the very next instruction, visible at the end of sum in loop.s below. c2 removes these.

The outermost block is where storage is set up (2903–2908). If profiling was asked for, a PROFIL record goes out first. Then blkhed reads the local declarations, assigns the parameter offsets and returns the number of bytes used below r5, which becomes the argument of SAVE, from which c1 generates jsr r5,csv and the stack adjustment. blkhed also writes SETREG, telling c1 how many registers the register variables have left for it to use.

Nested blocks have no declarations of their own in this C. Only the outermost block of a function reads any: an inner { goes straight to reading statements (2909–2916).

Labels

Labels generated by the compiler are numbers taken from the counter isn, which also numbers strings and floating constants. They come out as L1, L2, and so on. c1 starts its own counter at 10000 (4875) and c2 at 20000, so that the labels each pass invents never collide with those of the pass before. That is why the labels in the generated code are in three ranges.

A label written by the programmer is a name followed by a colon (3077–3091). It is given the class STATIC and the type ARRAY, and a label number, and from then on it is treated much like a static array: its name used in an expression is the address of the code at that point. A label used before it is defined is created the same way by tree (chapter 5).

That treatment makes goto interesting. goto x; with a plain label is recognised by simplegoto (3994–4012) and becomes a BRANCH. Anything else is compiled by dogoto (4061–4069) as an expression: the operand is read with tree, * is applied to it, and the result is wrapped in a JUMP node, which c1 turns into a jmp instruction. Since a label is an array, *label is the code at the label. But the operand can be any expression that yields an address, so a variable can hold the address of a label, obtained just by naming it, and goto can jump to it. The Sixth Edition had computed goto without ever mentioning it.

cgoto.c

main()
{
        int *where, n;

        n = 0;
        where = two;
        goto where;
one:
        printf("one\n");
        n++;
two:
        printf("two\n");
        if (n == 0) {
                where = one;
                goto where;
        }
}

a.out

two
one
two

Both goto where statements compile to jmp *-10(r5): jump to the address held in where. Note that two is used before it is defined, and that where is declared as int *; any pointer would do.

The control statements

statement (2889–3102) reads one statement. After a keyword it switches on which keyword it was. The labels needed for break and continue are kept in the globals brklab and contlab, and each loop saves the old values in local variables and restores them at the end, so that loops nest. chconbrk complains if a break or continue appears where its label is zero.

The layouts are these. c is the controlling expression, and “branch if false c” is a CBRANCH record whose third field is 0.

The while loop tests at the top and jumps back at the bottom, so each iteration costs a conditional branch and a jump. A loop that tested at the bottom would save the jump, and c2 rewrites loops that way (chapter 13); c0 keeps things simple.

if has special cases for the commonest bodies that are a single jump (2932–2971). if (c) goto L;, if (c) break;, if (c) continue; and if (c) return; are each compiled into one conditional branch to the target, “branch if true c”, instead of a branch around an unconditional jump.

The for statement

The layout of for in the table has a problem: the increment expression n is written in the source before the body s, but its code has to come after. The compiler reads the source only once, and does not store statements, so how does the increment end up in the right place? forstmt (3107–3151) solves this neatly.

c02.c
 3134          l = contlab;
 3135          contlab = isn++;
 3136          st = tree();
 3137          sline = line;
 3138          if ((o=symbol()) != RPARN)
 3139                  return(o);
 3140          ss = treespace;
 3141          treespace = space;
 3142          statement(0);
 3143          sline1 = line;
 3144          line = sline;
 3145          label(contlab);
 3146          rcexpr(st);
 3147          line = sline1;
 3148          treespace = ss;
 3149          branch(l);
 3150          return(0);

The increment is parsed with tree as usual, but not written out: the pointer to its tree is kept in st. The tree lives in the expression space osspace, and the next call to tree, for the first expression of the body, would normally start allocating from the beginning of that space again and overwrite it. So forstmt moves the start of the space, treespace, up to the current allocation point, space. The body's expressions are then built above the increment's tree. After the body, the increment is written out with rcexpr, and treespace is put back.

The line number is juggled too. It is saved after the increment is read, so that an error found while writing it out is reported on the line of the for, not the end of the body.

Nested for loops each set treespace a little higher, so a deep nest of loops with large increment expressions uses up the 500 words of expression space, and the result is “Expression overflow”.

If there is no increment, none of this is needed, and the loop is closed with a jump straight back to the test (3128–3133). If there is no test, there is no conditional branch, and the loop runs until something breaks out of it.

Here are the two functions of loop.c compiled without optimization. clear uses do, and sum uses for with if and else inside. The labels L6 to L10 in sum are, in order: the test, the exit, the continue label in front of the increment, the else, and the end of the if.

loop.c

int v[100];

clear()
{
        register int *p, n;

        p = v;
        n = 100;
        do
                *p++ = 0;
        while (--n);
}

sum()
{
        register int *p, s;

        s = 0;
        for (p = v; p < &v[100]; p++)
                if (*p != 0)
                        s =+ *p;
                else
                        s =- 1;
        return(s);
}

Two things in this output come from c1 rather than from the layout. In clear, *p++ = 0 became the single instruction clr (r4)+, using the PDP-11's autoincrement mode. In sum, the loop test p < &v[100] is a pointer comparison, so it branches with jlos, the unsigned branch, and the address &v[100] has been folded into the constant $310+_v.

The switch statement

switch evaluates its expression into r0, using the node RFORCE, and then calls pswitch (3177–3200) to compile the body. case and default are just labels. When statement reads case 3: it evaluates the constant, allocates a label, writes it, and records the pair in the table swtab (3026–3041). Since the code that chooses between the cases can only be written after all the cases have been seen, pswitch first writes a jump to a label L1, then compiles the body, then writes a jump past the switch for when the body falls off the end, and then, at L1, a SWIT record listing the default label and all the value and label pairs.

swtab is shared by all the switches being compiled at once. A nested switch starts its entries where the outer one's currently end, at swp, and puts swp back when it finishes, so the table behaves as a stack. Like everything else in c0, its size is fixed: 200 cases for all the active switches together.

What c1 does with the SWIT record is the subject of chapter 12. For the curious, the vowels.c switch appears in the intermediate file in chapter 3.

Expressions and return

A statement that starts with anything other than a keyword or a label is an expression statement. It is read with tree and written with rcexpr (3093–3094), which is all it takes: the expression's value is not needed, and c1 compiles it for its side effects only.

return is compiled by doret (4075–4089), with a trick. The value has to be converted to the function's return type, and the code to do that is in build. So doret pretends to assign the value to funcblk, a fake name node whose type is the function's return type and whose storage class is register 0 (1371):

c04.c
 4075  doret()
 4076  {
 4077          register struct tnode *t;
 4078  
 4079          if (nextchar() != ';') {
 4080                  t = tree();
 4081                  *cp++ = &funcblk;
 4082                  *cp++ = t;
 4083                  build(ASSIGN);
 4084                  cp[-1] = cp[-1]->tr2;
 4085                  build(RFORCE);
 4086                  rcexpr(*--cp);
 4087          }
 4088          branch(retlab);
 4089  }

build(ASSIGN) inserts whatever conversion the assignment needs. doret then throws away the assignment and keeps only its right operand, cp[-1]->tr2, now converted, and wraps it in RFORCE, which tells c1 to leave the value in r0. A jump to the exit label follows. A function returning double gets its value converted to double, and one returning char * gets no conversion, all without any code specific to return.
