Chapter 6

Types and Conversions

  1. A type in sixteen bits
  2. What build does
  3. Conversions
  4. Constant folding

The parser of the last chapter decides the shape of an expression. Every time it applies an operator it calls build (2116–2315), and it is build that makes the tree a C tree rather than just an arithmetic one: it works out the type of every node, inserts conversions where the operand types differ, multiplies integers added to pointers by the size of what they point to, and rewrites subscripts, structure references and function names into simpler operations. This chapter describes the type representation first and then build.

A type in sixteen bits

A type is a single int. The low three bits give the basic type (1182–1190):

ValueNameSize
0INT2
1CHAR1
2FLOAT4
3DOUBLE8
4STRUCTfrom dimtab
5RSTRUCT, a structure not yet definedunknown
6LONG4
7NOTYPE, used internally

Above them, starting at bit 3, come two-bit fields, each of which is a type modifier: PTR (1), FUNC (2) or ARRAY (3) (1197–1199). The field in bits 3 and 4 is the outermost modifier, the one you meet first when using the object. So a pointer to char is 010|1, 011 octal; an array of pointers to char, such as argv, has ARRAY in bits 3 and 4 and PTR in bits 5 and 6, making 071; and a function returning a pointer to char is 0121. Six modifiers fit, which is more than anyone needed.

With this layout, the two operations that the compiler needs most are shifts. decref (3813–3823) removes the outermost modifier, as the * operator does to a pointer or a call does to a function, by shifting the modifier bits right by two and keeping the base. incref (3829–3832) shifts them left and puts PTR in the vacated field, as & does. The test “is this a pointer?” is (t&XTYPE)==PTR, and several places use the shortcut t>=PTR to mean “is any kind of reference”, which works because every modified type is numerically larger than every basic one.

The type word does not say how big an array is, or which structure a STRUCT is. That information lives in dimtab, and each node and symbol carries an index into it (chapter 3). length (3939–3979) combines the two to give the size of an object in bytes, and plength (3920–3933) the size of the object a pointer points to, which is what pointer arithmetic needs.

The type word

Choose a basic type, then wrap it in modifiers. Each wrap makes the current type the thing pointed to, returned, or stored in the array, and so pushes the existing modifiers up two bits. You can also click individual bits.

What build does

build(op) pops one or two operands from the parser's operand stack, makes a node with operator op, and pushes it. In between, it does a good deal. It is easiest to follow in the order the code is written.

Rewrites before anything else

A subscript is not an operator in its own right. a[i] is turned into *(a+i) by building a + and then a * (2123–2129), so that everything that follows, including the scaling of i, is the ordinary treatment of addition and indirection. This is the identity that defines subscripting in C, applied literally, and it is why i[a] works too.

Next, the operands are normalised (2131–2155). disarray (2413–2428) turns an operand whose type is an array into a pointer to its first element, by changing the node's type to the element type and applying &. chkfun (2397–2407) does the same for a function name, which becomes a pointer to the function. These two rules are why an array name, used in an expression, is a pointer. The exceptions are the operand of &, and the function of a call, which must stay a function.

sizeof is resolved here too, simply by replacing the operand with a constant equal to its length (2136–2149). The comment admits a bug. When the member of a structure is an array, the . operator produces its address, a pointer, rather than the array itself (see below), so by the time sizeof sees it, the operand is a pointer and its size is 2. The real compiler agrees; in decl.c, below, sizeof np->name prints as 2 although name is char[5].

Operators that need no conversion

A group of operators is dealt with immediately (2158–2241). ,, &&, || and ? just make a node. A call checks that its operand is a function and takes its type from the function's return type.

* and & cancel each other: *&x is x, and &*p is p with its type adjusted. & may otherwise only be applied to a name; anything else is an “Illegal lvalue”. Since array subscripts and structure members all become * of something, this one rule covers &a[i] and &s.m.

Structure references

a->b is rewritten as (*a).b (2207–2215). The operand a is given the type “pointer to structure” whatever it really was, which is how the language lets any pointer, or even an integer, be used on the left of ->. Then the . case (2217–2241) does what its comment calls a fairly complicated process. The member name on the right carries the member's type and its offset in the structure. The left operand is retyped as if it were an object of the member's type, its address is taken, the offset is added as a constant of the special type NOTYPE, and the sum is dereferenced. So

s.m      becomes    *(&s + offset of m)
p->m     becomes    *(p + offset of m)

where the addition is a plain byte addition. The NOTYPE on the constant is how the addition knows not to scale it (2263–2266). For an array member the final * is omitted, since the address is already what is wanted, and for a bit-field the result is wrapped in a field-selection node, FSEL, that records the field's width and position for the second pass. Neither . nor -> survives into the intermediate file.

Because the member carries its own offset, the structure on the left is never consulted. Any member name can be applied to any object, a property the Sixth Edition kernel relied on heavily, for example to treat a pointer to a buffer header as an array of integers.

Checks

For the remaining operators the flag bits in opdope decide what to check (2243–2248). An operator with LVALUE set, which includes the assignments, ++ and --, calls chklval (2521–2529): its operand must be a name or a * node. This is where the bit-field restriction comes from. A field is neither, it is an FSEL node, so assigning to a field fails with “Lvalue required”, and the Sixth Edition compiler can read bit-fields but never store into them. LWORD and RWORD mark operators that need integer operands, such as & and <<, and chkw (2436–2444) enforces them.

Unary operators then need only a type: the same as the operand's, except for the two conversion operators (2249–2257).

Conversions

For a binary operator, build looks up the pair of operand types in a four-by-four table, cvtab (4280–4302). lintyp (2450–2468) sorts types into four classes: integer (including char), floating, long, and pointer.

c05.c
 4297  char cvtab[4][4] {
 4298  /*              int     double          long            ptr */
 4299  /* int */       0,      (FTI<<4)+ITF,   (LTI<<4)+ITL,   (ITP<<4)+ITP,   
 4300  /* double */    ITF,    0,              LTF,            XX,
 4301  /* long */      ITL,    (FTL<<4)+LTF,   0,              XX,
 4302  /* ptr */       ITP,    XX,             XX,             PTI

Each entry is a conversion code (1281–1291). An entry whose high four bits are set means “convert the left operand”, with the low four bits saying how. For int + double the entry is (FTI<<4)+ITF: the left operand is the one to convert, and the conversion is ITF, integer to floating. The FTI in the high half matters for assignments. The left side of an assignment cannot be converted, so the result type is the left side's, and the conversion in the high half, FTI, is applied to the right side instead (2272–2278). The comment above the table explains this in its own words (4280–4296).

Pointers need their own rules (2279–2296):

  • Integer and pointer (ITP): the integer is multiplied by the size of the object the pointer points to. convert (2322–2356) does this by building a * node, which the second pass will turn into a shift when the size is a power of two. A plain assignment of an integer to a pointer, or the reverse, is accepted with no conversion at all.
  • Pointer and pointer (PTI): allowed for subtraction, which gives an int that is then divided by the object size, and for comparison, which uses the unsigned comparison operators LESSP and so on. Other operations are illegal, except, oddly, between two char pointers.
  • Pointer and floating or long (XX): “Illegal conversion”.

Structures cannot be operands of anything but . and &: there is no structure assignment, and the attempt draws “Unimplemented structure operation” (2259–2262).

After the conversion, a relational operator's result is made int, fold is given a chance to evaluate the node if both operands are constants, and otherwise the node is made (2307–2314).

build() on a binary operator

Pick the types of a and b and an operator to see what build does with a op b. The logic follows 2258–2314.

The effect of these rules shows clearly in the generated code. Here is a small program doing pointer arithmetic, its output, and part of the code for it.

ptr.c

int v[10];

main()
{
        int *p, *q;
        char *s, *t;

        p = &v[1];
        q = &v[7];
        s = "abcdef";
        t = s + 4;
        printf("%d %d\n", q - p, t - s);
        p = p + 3;
        printf("%d\n", p - v);
}

a.out

6 4
4

ptr.s (part)

mov	$2+_v,-10(r5)      / p = &v[1]
mov	$16+_v,-12(r5)     / q = &v[7]
...
mov	-12(r5),r0         / q - p
sub	-10(r5),r0
asr	r0                 / divided by 2
...
mov	-10(r5),r0         / p = p + 3
add	$6,r0              / 3 scaled to 6 bytes
mov	r0,-10(r5)

&v[1] became the constant address 2+_v: the subscript turned into *(v+1), the 1 was scaled to 2, and &* cancelled, leaving an address the second pass could fold into a single operand. t - s, the difference of two char pointers, needed no division at all.

And here is the structure example that shows both the sizeof bug and the bit-field layout problem described in the next chapter.

decl.c

struct node {
        int     value;
        char    flag;
        int     kind:3;
        int     mark:1;
        int     count;
        struct  node *next;
        char    name[5];
};

struct node tab[10];
int (*fp)();
char *argv[4];
int matrix[3][4];

main()
{
        struct node *np;

        np = &tab[2];
        printf("%d %d %d\n", sizeof tab[0], sizeof matrix, sizeof np->name);
        printf("%d %d\n", &np->count - &np->value, &np->next - &np->value);
        printf("%d\n", np->kind);
}

a.out

14 24 2
2 3
0

The first line gives the size of a struct node (14), of matrix (24), and sizeof np->name, which should be 5 but is 2. The second gives the distance in words from value to count and to next: 2 and 3, which puts count on top of the bit-fields. Chapter 7 explains.

Constant folding

fold (2537–2604) evaluates an operator whose operands are integer constants, replacing the node by a constant. It handles the arithmetic and logical operators and unary minus and complement. Its comment says that more folding happens in the second pass, and this one exists mainly so that constant expressions can be used where the first pass needs a number: array bounds, case labels and bit-field widths, all read by conexp. Relational operators are not folded, which is why the max(10, 7) of chapter 2 compiled into an actual comparison of two constants:

.globl  _onunix
.data
_onunix:
1
.globl  _main
.text
_main:
~~main:
jsr     r5,csv
cmp     $7,$12
jge     L10000
mov     $12,(sp)
jbr     L10001
L10000:mov      $7,(sp)
L10001:mov      $L2,-(sp)
jsr     pc,*$_printf
tst     (sp)+
L1:jmp  cret
.globl
.data
L2:.byte 45,144,12,0

Nothing in either pass folds 10 > 7, so the code compares $7 with $12 and branches, every time the function is called.
