Most compilers of the early 1970s generated code with large amounts of hand-written logic: a routine for each operator, full of cases for each kind of operand. c1 has a routine for very few operators. Instead, the knowledge of which instructions implement which operator on which operands is written as data, in table.s: for each operator a list of patterns, each describing a kind of operand pair, and for each pattern a template of assembly language with holes in it. Code generation is then a search for the first pattern that fits, followed by the expansion of its template. The table is 1255 lines long, and is the single largest part of the compiler.

Four tables

An expression can be compiled for different purposes, and there are four tables, one for each:

TablePurposeStarts at
regtableave the value in a register[[table.s:8]]
efftabcompute it only for its side effects, and set the condition codes[[table.s:713]]
cctabonly set the condition codes, for a branch[[table.s:1072]]
sptabpush the value onto the stack, for a function argument[[table.s:1193]]

The same expression gets quite different code from each. a = b for its effect is mov _b,_a; for its value in a register it needs another instruction to fetch the result; a + 1 for the stack can be mov _a,-(sp); inc (sp). Only regtab has to be complete. When a node cannot be compiled with one of the others, the code generator falls back on regtab and then adds a tst to set the condition codes, or a mov to push the register ([[c10.c:326-345]]). So the other tables need only contain the cases where they can do better than that.

A fifth table, lsptab, has no entries of its own. It is sptab with one difference: it stores into (sp) instead of pushing onto -(sp). It is used for the first argument of a call, which goes into the free word at the top of the stack (chapter 1). match quietly substitutes sptab for it ([[c10.c:88-89]]), and the difference is made when the template is expanded.

Each table starts with a directory that maps operator numbers to labels ([[table.s:8-53]]). Operators with the same code share a label: +, -, |, &~ and << all use cr40 in regtab, since each is a single two-operand instruction, and only the instruction's name differs.

Patterns

Here is the regtab entry for those operators, in part:

[[src:table.s:230-271]]

Each line beginning with % is a pattern, describing the left and right operands, and the lines that follow, up to a blank line, are its template. A pattern describes each operand with a letter for how hard it is to compute, then optional letters for its type, then optionally *. The difficulty letters are an upper bound:

LetterMatches
zthe constant 0
1the constant 1 (or 0)
ca small positive constant
ra register variable (or a constant)
aanything addressable: a name, a constant, an address, or an indirection through a name
eanything that can be computed in the registers still free
nanything at all

The type letters are w for a word, b for a byte, f for float or double, d for double, and l for long; no type letter means a word or a byte. A * means the operand must be an indirection, *x, and the template will compute the pointer x and address through it. So %n,aw reads: the left operand is anything, the right is an addressable word. %nf,nd* reads: the left operand is any floating value, the right an indirection through any pointer to a double.

The patterns are tried in order, and the first that fits is used, so the order matters: cheap, specific cases come first, and the general case %n,n, which evaluates the right operand onto the stack, comes last. For +, the list starts with adding zero, which costs nothing, and adding one, which is an inc.

Templates

The templates are assembly language with embedded macros:

MacroExpands to
A1, A2the address of the first or second operand, as an assembler operand
A1+the address of its second word, for the low half of a long
A1'the address without its side effect: (r2) for (r2)+, when an operand is used twice
I, I'the instruction for this operator, or its alternative form
B1, B2, BEb if the operand, or either operand, is a char, for the byte form of the instruction
BFf if the operation is floating
R, R1, R-, R+the result register, the next one, and its neighbours
F, S, Hcompile the first operand, the second operand, or the whole tree, into R
#1, #2the constant offset of an indirection, as in #1(R)
Ta tst, if the condition codes are not already set
Vadc or sbc, to carry into the high word of a long

F, S and H are what make the scheme recursive: each calls the code generator on a subtree, and can be modified by following letters. F* compiles, not the operand *x, but x, so that the template can then address #1(R). S1 compiles into R1 instead of R. SS compiles onto the stack, and FC for the condition codes.

I is looked up in the table instab in c1t.s ([[c1t.s:8-60]]), which gives two names for each operator. The alternative, I', is used for special cases: for = the two are mov and clr, for == they are cmp and tst, for + they are add and inc. That is how the pattern %n,1 above, with template F then I' R, produces inc r0 for an addition of one, and dec r0 for a subtraction.

So the template for %n,aw, which is

F
IB2	A2,R

means: compile the left operand into the register; then emit the operator's instruction, with a b suffix if the right operand is a char, taking the right operand's address as the source and the register as the destination. For x + y this is mov _x,r0, then add _y,r0. For x - 1 it is not used, because %n,1 comes first.

Templates are often shared. %[add1:] names the template that follows, and a later line % [add1] uses it again. Multiplication in cr42, for instance, uses the templates of cr40 unchanged, since mul works like add once its register has been chosen to be odd. The relational operators in cctab share the templates of assignment in efftab, which is why comparisons come out with their operands in the unexpected order noted in chapter 1: mov A2,A1 becomes cmp A2,A1. Chapter 11 explains how the branch is reversed to suit.

Translating the tables

table.s is not assembled as it stands. It is first passed through cvopt ([[cvopt.c:7-291]]), a small translator whose output is ordinary assembly language ([[run:4-6]]). cvopt turns each pattern into four bytes, a difficulty and a type for each operand, followed by a pointer to the template, and each template into a string. Along the way it abbreviates the macros into single characters, as its comment records ([[cvopt.c:10-39]]): A1 becomes A, A2 becomes B, F becomes G, R becomes I, and so on. A subtree macro is followed by one more letter that encodes its modifiers: A plus 1 for *, 2 for S, 4 for C and 8 for 1, so that F becomes GA and F* becomes GB. cexpr decodes them by subtracting 'A' ([[c10.c:545-560]]). A tab at the start of a line becomes the top bit of the next character. The difficulty letters become numbers that match can compare with the result of dcalc: z is 4, 1 is 5, c is 8, r is 9, a is 16, e is 20 and n is 63, and * adds 0100.

The structures that result are declared in c1h.c ([[c1h.c:51-62]]): a struct table entry pairs an operator with a list of struct optab, and each optab holds the four bytes and the string.

Matching

match ([[c10.c:77-142]]) is given a tree, a table and the number of free registers. It finds the operator in the table, and then tries the patterns in order ([[c10.c:125-140]]). For each operand it computes a difficulty with dcalc ([[c11.c:148-186]]):

dcalcFor
4the constant 0
5the constant 1
8any other positive constant
9a register variable
12a name, an address, a negative constant, (r)+, -(r), or * of a name or constant
20anything whose degree is no more than the number of free registers
24anything else

An operand fits a pattern if its difficulty is at most the pattern's, if it is an indirection when the pattern demands one, and if its type is compatible, which notcompat ([[c11.c:188-211]]) decides. So a constant 1 fits 1, c, a, e and n, and the first pattern in the list that allows it wins.

There is one more trick in match. If either operand is a conversion, such as int to double, it first tries to match the tree with the conversion removed ([[c10.c:101-118]]). The tables contain entries for mixed types where the machine can do the conversion as part of the operation, and these are found that way. The comment gives the example of assigning a double to an int: movf double,fr0; movfi fr0,int converts on the way out of the register, so the double never needs to be converted into an int in a register first.

An example

Here is how a = b + c*d, from expr.c, is compiled, as the tracing c1 recorded it. After optim the tree is a = (c*d) + b, the product moved first because it is harder.

  1. The statement is compiled for effect, and efftab's entry for =, ci80, is searched. The left operand a is addressable; the right is not. The first pattern that fits is %a,n ([[table.s:754]]), whose template is S, then IB1 R,A1: compute the right side into a register, then move it into a.
  2. S compiles (c*d) + b into a register using regtab. The entry cr40 matches %n,aw, since b is an addressable word: F, then add _b,R.
  3. F compiles c*d into the register. cr42 matches %n,aw again, reusing the add1 template: F, then mul _d,R. Because this is a multiplication, the register has been made odd: r1.
  4. F compiles c, a leaf, which is done through the operator LOAD and cr106, pattern %a,n: mov _c,r1.

Unwinding, the output is

mov	_c,r1
mul	_d,r1
add	_b,r1
mov	r1,_a

which is exactly the code in expr.s. The trace viewer in the next chapter shows this breakdown for every statement of several programs.
