With the trees prepared and the tables understood, what remains is the driver that connects them. It is in c10.c and consists of two mutually recursive routines. rcexpr ([[c10.c:165-351]]) takes a tree, a table and a register, handles the cases that the tables cannot, and tries rearranging the tree; cexpr ([[c10.c:362-688]]) finds a template with match and expands it. Conditional branches are handled separately, by cbranch in c11.c.

Registers

Every call carries a register number, the register in which the result is wanted. The registers from that one up to nreg are free for the computation. nreg is set for each function from the SETREG record: with no register variables it is 4, so r0 to r4 are available; each register variable, allocated from r4 down, takes one away ([[c11.c:800-802]]). An expression that needs more than that has to use the stack, which the tables arrange by choosing patterns with SS when an operand's degree exceeds the free registers. If a template nevertheless asks for a register beyond nreg, the compiler gives up with “Register overflow: simplify expression” ([[c10.c:616-617]]).

The result does not always end up where it was asked for, and every routine returns the register where it actually is. oddreg moves a multiplication or division to an odd register, as mul and div require ([[c11.c:263-282]]); a product or a remainder ends up in that register, and a quotient in the even register below it. And when a template computes a subtree into another register, cexpr may simply adopt that register instead of moving the value back, if nothing else needs the original ([[c10.c:586-596]]).

rcexpr

rcexpr begins by dealing with operators that need more than a template ([[c10.c:186-302]]):

  • CBRANCH, a conditional jump, goes to cbranch (below).
  • INIT, an initializer that is an address, just prints the address.
  • RFORCE computes its operand into a register and moves it to r0, for return and switch.
  • , compiles its left operand for effect and continues with the right.
  • NAND, when only the condition codes are wanted, becomes TAND, the test operator, and its operand is complemented back, so that if (a & 010) becomes bit $10,_a rather than a copy and a bic.
  • Multiplication and division by powers of two become shifts, through pow2.
  • Calls, described below.

Then it tries two transformations that rearrange the order of evaluation, and only after that calls cexpr. If cexpr fails with the requested table, rcexpr tries regtab and adds the instruction needed to turn a value in a register into what was wanted ([[c10.c:326-345]]): tst for condition codes, a push for the stack.

Postponing increments

C's postfix operators are awkward: x + y++ needs the old value of y for the sum and the new one stored back. delay ([[c10.c:818-858]]) observes that this is the same as x + y followed by y++, compiled for effect. It searches the operands for a postfix ++ or -- applied to a name, replaces it by the name, compiles the tree, and then compiles the increment afterwards with efftab, where it is a single inc or add. That is how *p++ = *q++ in expr.c became

mov	*_q,*_p
add	$2,_p
add	$2,_q

with the increments delayed out of the assignment. When the pointer is a register, as in gen.c, unoptim had already turned *q++ into the autoincrement mode, and the result is mov *_p,(r4)+ followed by add $2,_p.

Reordering

reorder and sreorder ([[c10.c:695-805]]) handle expressions that involve register variables. Their comment explains the two cases. An assignment to a register buried inside a larger expression, x + (r = y), is done first, and replaced in the tree by the register. And r = x + y is compiled as r = x; r =+ y, which computes into the register variable directly rather than into a temporary that is then copied, unless y is r itself, in which case the rewriting would be wrong. gen.c has an example of the exception: i = a + i is computed in r0 and copied into r3.

cexpr

cexpr handles three more cases before it looks at the tables.

If the value of a relational or logical operator is wanted, rather than a branch on it, there is no instruction that produces it. So cexpr compiles it as a branch, with 0 and 1 loaded on the two paths ([[c10.c:383-391]]). This is where the labels numbered from 10000 come from. x = a < b in gen.c becomes

cmp	_b,_a
jgt	L10002
clr	r0
jbr	L10003
L10002:mov	$1,r0
L10003:mov	r0,_x

The conditional operator ?: is compiled the same way, with the two operands in the two branches ([[c10.c:392-407]]).

A leaf, a name or constant whose value is wanted in a register, is compiled by chkleaf ([[c10.c:883-897]]). It wraps the leaf in a node with the operator LOAD, which appears in every table as the case for simply fetching an operand, and compiles that. In the traces, every mov of a variable into a register comes from LOAD.

Then match is called. When only the condition codes are wanted, cexpr tries efftab first, since code compiled for its effect leaves the condition codes set as a by-product, except for postfix increments, which set them for the wrong value ([[c10.c:431-444]]).

Expanding a template

The rest of cexpr is the template interpreter ([[c10.c:445-688]]), a loop over the characters of the template string as translated by cvopt. Ordinary characters are printed. The macro letters, in their translated form, select cases: A and B print the address of an operand with pname; M prints the instruction from instab; C, D, L and P print the b and f suffixes; I and J print registers.

The subtree macros, G, K and H (F, S and H in the source), are the interesting ones ([[c10.c:528-597]]). The letter after them selects a table: sptab for S, cctab for C, regtab otherwise. It also selects a register, reg1 for 1. With *, the subtree compiled is the pointer beneath the indirection, and if that pointer has the form x + constant only x is compiled, since the constant will be printed by #1 as an offset. Then rcexpr is called on the subtree, recursively.

The first operand of a division is compiled with the table cregtab instead of regtab. cregtab is declared ([[c10.c:23]]) but never given a value, so it is a null pointer, used only as a marker. cexpr treats it as regtab ([[c10.c:429-430]]), but rcexpr does not try to postpone increments out of it ([[c10.c:307-314]]), which could otherwise leave the dividend somewhere other than the register pair div works on.

Function calls

Calls are compiled in rcexpr ([[c10.c:249-278]]), not by a template, because the arguments must be compiled exactly once and in a particular order. The arguments are a chain of , nodes; rcexpr walks it from the right, so that the last argument is pushed first, and compiles each with comarg ([[c10.c:906-922]]).

comarg uses sptab to push the argument onto the stack, except for the first one pushed when nothing else is on the stack. That one goes, through lsptab, into the free word at the top of the stack, and needs no popping afterwards. nstack counts the words the code generator has pushed, so it knows whether the stack is empty. Then the call itself is compiled through the table, as the operator CALL1 if the free word was used and CALL2 otherwise. Their templates are the same, but I prints *$ for CALL1 and nothing for CALL2; the two strings in c1t.s are one string and its terminating null byte ([[c1t.s:50-51]]). So printf("%d\n", n) produces jsr pc,*$_printf while a call with no arguments produces jsr pc,_g. Both instructions are four bytes long and do the same thing; the source does not say why they are distinguished.

Finally popstk ([[c11.c:581-597]]) removes the arguments that were pushed, choosing the shortest instruction: tst (sp)+ for one word, cmp (sp)+,(sp)+ for two, and add for more. With the free word, a call with up to three one-word arguments needs at most a two-byte instruction to clean up.

A call destroys the registers the callee uses, so a call's degree is high, and an expression with two calls, f1(a) + f2(b) in gen.c, keeps the first result on the stack while it makes the second call:

mov	_b,(sp)
jsr	pc,*$_f2
mov	r0,-(sp)
mov	_a,-(sp)
jsr	pc,_f1
tst	(sp)+
add	(sp)+,r0

Note that f2 is called first, since the right operand of + is pushed on the stack by the template SS, and that f1's argument is pushed with -(sp) rather than stored in the free word, because the stack is no longer empty, so that call is a CALL2.

Branches

A condition in an if or a loop arrives as a CBRANCH node: a tree, a label, and whether to jump when the tree is true or when it is false. cbranch ([[c11.c:492-563]]) compiles it without ever computing a truth value.

&&, || and ! are handled by recursion ([[c11.c:505-529]]). To jump if a && b is true, jump past the whole thing if a is false, then jump to the target if b is true. To jump if it is false, jump to the target if either is false. || is the mirror image, and ! just flips the sense. The result is the familiar short-circuit code, with labels from c1's own counter:

Any other condition is compiled with cctab, which leaves the condition codes set, and followed by a conditional jump chosen by branch from branchtab ([[c1t.s:63-85]]). Each entry has two instructions: the jump for the condition, and the jump for its opposite, used when the branch is to be taken on false.

Which condition to test takes some care ([[c11.c:549-562]]). If the tree is not a comparison, its value was simply tested, and the jump is on non-zero. If it is a comparison with zero, the code was a tst of the left operand, and the operator maps directly onto a jump; this is marked by adding 200 to the operator number, which selects a second set of entries in branchtab. Otherwise the code was a cmp produced by a template shared with assignment, cmp A2,A1, with the operands in the order right, left. Since cmp sets the condition codes from its first operand minus its second, the test must be reversed, and maprel does that: a < b is tested as b > a. That is why while (a < b) above compares _b with _a and leaves the loop with jle.

The second set of entries has a surprise for pointers. Pointers are compared unsigned, and an unsigned number is never less than zero. So for p < 0 the entry's two jumps are /nop and jbr ([[c1t.s:82]]): never jump, and always jump. /nop is not an instruction; / starts a comment in the assembler, so the “jump” disappears.

The tst instructions are left behind, testing a value nobody looks at. c2 removes the unreachable call to g, but not the tests.

For long comparisons there is no compare instruction, so cbranch subtracts and tests the 32-bit difference with ashc $0,r0, a shift by zero that sets the condition codes for the register pair ([[c11.c:537-548]]). Floating comparisons set the floating-point unit's condition codes, which must be copied to the processor's with cfcc before the jump.
