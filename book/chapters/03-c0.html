This chapter describes the data that the first pass works with: where it keeps names, how it builds expression trees, and what it writes out. The routines that parse C are the subject of the next five chapters; here we are concerned with what they leave behind.

The main program

c0 is called by cc with three file names: the source, and two temporaries it must create ([[c00.c:1-12]]). Its main ([[c00.c:56-100]]) opens them, marks the keywords in the symbol table (see below), and then does all its work in a two-line loop:

[[src:c00.c:90-93]]

A C file, in this dialect as in modern C, is a sequence of external definitions: declarations of global variables, with or without initializers, and function definitions. extdef ([[c02.c:12-57]]) reads one of them. blkend ([[c02.c:612-628]]) then clears out everything that was local to it. When the input runs out, main writes an end-of-file marker to each of the two output files ([[c00.c:94-96]]) and exits with a status that tells cc whether there were errors.

There is no parse tree for the program as a whole and no representation of a function. c0 writes each statement's code to the output as soon as it has read it, and only an expression is ever held in memory as a tree. As soon as the expression is complete, it is written out and the space it occupied is reused.

Fixed sizes

Every table in c0 is a fixed-size array, and the sizes are set at the top of the header ([[c0h.c:13-22]]):

ParameterValueLimits
ncps8characters per symbol
hshsiz200names in the symbol table at one time
cmsiz40operands on the parser's stack
swsiz200case labels in all the switches being compiled at one time
OSSIZ500words of storage for expression trees
dimsiz100array dimensions and structure sizes in a file
STRSIZ256characters in a string constant

Running out of any of them is fatal. The messages are ones every Sixth Edition programmer met sooner or later: “Symbol table overflow”, “Expression overflow”, “Dimension/struct table overflow”. The limit of 200 symbols is less severe than it looks, because the table only holds the names visible at one moment: the file's external names plus the locals of the function being compiled.

The symbol table

An entry in the symbol table is a struct hshtab ([[c0h.c:63-70]]):

[[src:c0h.c:63-78]]

hclass is the storage class: AUTO, EXTERN, STATIC, REG, a structure member MOS, a structure tag STRTAG, or an argument, all defined at [[c0h.c:253-264]]. htype is the type, encoded in sixteen bits as chapter 6 describes. hoffset is where the thing is: the offset from r5 for an automatic, the register number for a register variable, the label number for a static, the byte offset for a member of a structure.

hdimp is used in two ways, which is why the header declares a second, anonymous structure with the same beginning. For an array it holds, in its low byte, an index into dimtab, the table of array dimensions; the field is then called ssp. For a structure it holds, in its high byte, the index in dimtab where the structure's size is kept; the field is then called lenp. And for a bit-field member the same two bytes are called flen and bitoffs, the field's width and its bit position. The anonymous structures exist only so that these names can be used with ->. Since structure member names in this C are global and apply to any pointer, a declaration like the one at [[c0h.c:72-78]] is a way of saying “at byte 4 of whatever this points to there is a char called flen”.

hflag holds four flag bits ([[c0h.c:345-351]]). FNDEL marks names that must survive the end of a function; FNUND records that an “undefined” error has already been given for the name, so it is not repeated; FFIELD marks bit-fields. The fourth, FKEYW, is the interesting one.

Lookup

lookup ([[c00.c:108-148]]) finds the name held in the global buffer symbuf. It hashes the eight characters by adding them up, takes the sum modulo 200, and probes linearly from there until it finds either the name or an empty slot, in which case it enters the name. It returns the token NAME and leaves a pointer to the entry in csym.

Keywords are not in the table. Instead, at start-up, main computes the hash of every keyword and sets FKEYW in the slot where it would land ([[c00.c:84-89]]). When lookup finds FKEYW set in the first slot it probes, it searches the keyword table before looking any further ([[c00.c:121-123]]). Identifiers whose hash does not collide with a keyword's, which is most of them, never touch the keyword table. The flag belongs to the slot, not to whatever name happens to occupy it, and so blkend is careful to leave it alone when it clears a slot ([[c02.c:621-625]]).

A name that follows . or ->, or that is being declared as a structure member or tag, is read with a . in front of it ([[c00.c:290-293]]). The members of structures therefore have a name space of their own, .value being a different entry from value. But the dot takes one of the eight characters, so a member name is significant only to seven. lookup skips the dot when hashing ([[c00.c:116-117]]), which puts .int in the same slot as int, and findkw skips it when comparing ([[c00.c:161-163]]); that way a keyword is still recognised where a member name is expected, as in struct { int x; }, where int is read while the flag for members is on.

Deleting names

At the end of every external definition blkend goes through the whole table ([[c02.c:612-628]]). Any name that was used but never given a storage class is reported as undefined. Any name without FNDEL is deleted by clearing the first byte of its name. FNDEL is set on names that are entered while an external definition's declarator is being read, through the global xdflg, which lookup copies into every new entry ([[c00.c:142]], [[c02.c:23]]); so external names and the structure tags and members declared at the top level survive, and everything declared or mentioned inside a function goes.

Clearing entries out of the middle of a linearly probed hash table is normally a mistake, because it can break the chain of probes that leads to a later entry. Here it is safe for a reason that is easy to miss: names are deleted in the reverse of the order in which they were entered. Everything entered while a function is being compiled is deleted together at its end, and the entries that survive were entered before it began, so no surviving entry can lie further along a probe chain than a deleted one. The rule could in principle be broken by a declaration such as int f(a), g;, where the parameter name a is entered, to be deleted later, before the external name g; if g happened to collide with a, it would become unreachable. Nobody wrote declarations like that.

Tree nodes

Expressions are represented as trees whose nodes are all variations on struct tnode ([[c0h.c:24-29]]):

[[src:c0h.c:24-61]]

Every node begins with an operator and a type. An operator node has one or two operands, tr1 and tr2. A NAME node is a leaf that carries a copy of everything the second pass needs to know about a variable: its class, its offset, and, for an external, its name spelled out. The copying is deliberate, since the symbol table will be gone before the tree is used ([[c00.c:672-709]]). A constant is a leaf holding its value.

The third field of every node is dimp, the index of the array dimension information in dimtab, which the second pass calls degree and uses for something else entirely.

Nodes are allocated from the array osspace by gblock ([[c01.c:407-417]]), which simply advances a pointer, space. There is no freeing. When the parser starts a new expression it resets space to the start of the area ([[c00.c:477]]), abandoning the whole previous tree at once.

Nodes are built by block ([[c01.c:387-401]]), which is worth reading closely:

[[src:c01.c:387-401]]

It is called with a count of operands followed by the fields of the node in order, for example block(2, PLUS, INT, 0, p1, p2). It takes the address of its second parameter, op, and copies an+3 words from there into the new node. This works because on the PDP-11 the arguments of a call sit in consecutive words on the stack, in order, so the parameter list is itself laid out exactly like a node. One routine therefore builds nodes of every size. It relies on the calling convention in a way no modern compiler would allow, but it was perfectly reliable on the machine it was written for.

The intermediate file

Everything c0 writes goes through outcode ([[c04.c:301-343]]), which works like a small printf. Its first argument is a format of single-letter codes, and each code consumes one argument:

CodeWrites
Ban operator: a word with the operator number in its low byte and 0376 in its high byte
Na number: one word
Sa name: up to eight characters and a terminating zero byte
1, 0the constant word 1 or 0, used to separate and end lists of data

The 0376 in every operator word is a check. When c1 reads a word where it expects an operator, it verifies that the high byte is 0376 and stops with “Intermediate file error” if it is not ([[c11.c:643-647]]). Since the file has no other structure, a single disagreement between the passes about how many words follow some operator would otherwise send c1 reading garbage.

There are two kinds of record. Some are commands that c1 can act on at once: define a label, jump to a label, switch to the data segment, start a function. The others are pieces of an expression tree, and these come in postfix order. treeout ([[c04.c:56-100]]) writes a node's operands before the node itself, and rcexpr ([[c04.c:48-54]]) follows the whole tree with an EXPR record carrying the line number. The second pass rebuilds the tree with a stack: a leaf is pushed, an operator pops its operands and pushes itself, and at EXPR exactly one tree is left on the stack to be compiled. The postfix order saves any need for pointers in the file.

The second temporary file receives the text of string constants. The flag strflg redirects outcode to it ([[c04.c:309-311]]). Strings could not be written into the main file where they occur because they would land in the middle of the function's code, and c1 copies the second file onto the end of its output instead ([[c10.c:55-64]]).

What to look for

The initializer of s, which is &L1, the address of the string.

p++, which carries an explicit constant 1 as its second operand: the amount to add, already scaled for the pointer type.

The switch: an expression forced into r0, a jump to the end, the cases as plain labels, and then a SWIT record listing the values and labels.

The call to printf, whose arguments form a tree of , operators.

Errors

Errors are reported by error ([[c01.c:371-380]]), which prints the line number and a message and counts the error. It takes up to six arguments and passes them all to printf, whatever the format needs, another habit that only works because arguments are simply words on the stack.

After a syntax error the parser calls errflush ([[c02.c:665-673]]), which discards tokens until it reaches a semicolon or a brace. The token numbers were chosen so that this is a single comparison: EOF, SEMI, LBRACE and RBRACE are 0 to 3, and errflush skips while the token is greater than RBRACE.

Recovery is crude but effective, and c0 carries on to the end of the file, reporting further errors as it finds them. Its output is useless once an error has occurred, and cc does not run the second pass. Warnings are errors that decrement the error count after printing ([[c00.c:237-238]]); there is exactly one in the compiler.
