In 1977 John Lions of the University of New South Wales published two volumes for his operating systems course. The first was the source of the Sixth Edition Unix kernel, about nine thousand lines, printed with every line numbered. The second was a commentary that walked through that source and explained it. Bell Labs would not allow the books to be sold, and for twenty years they circulated as photocopies of photocopies. They were among the most widely copied computer science texts ever produced, because they did something no textbook did: they let you read a real system, all of it, with someone explaining it to you.

Lions covered the kernel. He did not cover the other large program in /usr/source that everything else depended on: the C compiler. This book tries to do for the compiler what Lions did for the kernel.

Why read this compiler

The Sixth Edition C compiler was written by Dennis Ritchie between about 1972 and 1975. It compiled the kernel, the shell, the editor and itself. It ran in 64 kilobytes of address space on machines that often had less real memory than that. And yet it is not a toy: it has a real type system with pointers, arrays, structures, long and double; it does register allocation, constant folding, strength reduction and a surprisingly clever treatment of conditional branches; and its code generator is driven by a table of templates, an idea that was new at the time and that later compiler generators made standard.

It is also short. The three passes together come to a little over nine thousand lines, a thousand of them code tables, and the code is dense but not obscure. Ritchie wrote in a plain, economical style, and his comments are usually enough to tell you what a routine is for. What the comments do not tell you is how the routines fit together, why the data structures are shaped the way they are, and which lines are there to work around the limits of a 16-bit machine. That is what the commentary is for.

Reading it is also a way to see C as it was before the book by Kernighan and Ritchie fixed the language in 1978. The compiler is written in its own dialect, and some of that dialect will look strange.

The C of 1975

You will meet the following differences almost at once. They are explained where they matter in the commentary, but it helps to know them before you open the listing.

  • Assignment operators are written the other way round. What is now x += 1 was x =+ 1. This caused a famous ambiguity, since x=-1 could mean x = -1 or x =- 1. The compiler takes the second reading and prints a warning (see chapter 4). The modern spelling came later, largely because of this problem.
  • Initializers have no equals sign. int isn 1; declares isn and initializes it to 1 ([[c00.c:16]]). Tables are initialized with a brace list that follows the declarator directly: int opdope[] { ... };.
  • There is no unsigned, short, union, typedef or enum. The complete list of keywords is the table at [[c00.c:25-54]]. Unsigned arithmetic is done by using pointers, which compare unsigned, and char is signed.
  • Structure member names are global. Every member of every structure lives in a single name space, which is why the kernel's structures prefix their members (p_stat, u_procp). It also means that x.y works on anything, and that the compiler source declares several anonymous structures just to give names to field offsets, as at [[c0h.c:31-36]].
  • Identifiers are significant to eight characters ([[c0h.c:13]]).
  • Functions return int by default and nobody declares them. Pointers and integers are freely mixed, and a pointer may be returned from a function declared as returning int. The routine block, which returns a pointer to a new tree node, is declared with no type at all ([[c01.c:387]]).
  • The preprocessor is optional. A file is run through it only if its first character is #. That is why every compiler source file begins with a line containing just #.

How the book is arranged

Part one is the listing. It contains all the compiler's source files, the cc command that runs the passes, and the two library routines, csv and cret, that every compiled function calls on entry and exit. The files are printed exactly as they were distributed. As in Lions, each file begins on a fresh sheet of fifty lines and the lines are numbered straight through the whole listing, from 100 to 10,938.

Part two is the commentary, which follows the path a program takes through the compiler.

  • Chapter 1 is an overview of the whole system, with a short introduction to the PDP-11 for readers who have never used one.
  • Chapter 2 covers cc, which runs the passes and contains the preprocessor.
  • Chapters 3 to 8 cover the first pass, c0, which parses C and writes expression trees to a temporary file.
  • Chapters 9 to 12 cover the second pass, c1, which reads the trees, rewrites them and generates assembly language from a table of code templates.
  • Chapter 13 covers the optional third pass, c2, which improves the assembly code.
  • Chapter 14 follows one small program through every stage.
  • An appendix collects the bugs, limits and oddities found along the way.

Part three is a cross-reference index of every identifier in the C files.

Numbers such as [[c00.c:185]] are line numbers. On a wide screen, clicking one opens the listing beside the text; on a narrow one it opens across the bottom of the screen.

Everything here was run

Every piece of compiler output in this book, every error message and every program result, was produced by the original binaries. The Sixth Edition distribution tape prepared by Ken Wellsch still exists; its disk images were booted on a simulated PDP-11/40, and a small script typed each example into the shell, compiled it with cc and captured what came back. Where the book says the compiler does something, you can see it doing it.

That practice turned up a few things the source alone does not make obvious. The standard c0 on the distribution tape cannot read floating-point constants at all, and a bit-field followed by an ordinary member can end up sharing storage with it. Both are explained where they occur.
